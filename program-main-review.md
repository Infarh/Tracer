# Tracer: проблемы и модернизация основной функции

Фокус: только логика трассировки в [Tracer/Program.cs](Tracer/Program.cs), без подсистемы автообновления.

## 1) Проблемы (исправления)

### P0
- [x] Возможны фоновые незавершенные задачи и неучтенные ошибки после первого ответа ICMP
  - Где: [Tracer/Program.cs](Tracer/Program.cs#L195), [Tracer/Program.cs](Tracer/Program.cs#L224)
  - Риск: нестабильное поведение под нагрузкой, сложная диагностика ошибок
  - Действие: после выбора первого результата корректно завершать/дожидаться остальные задачи или упростить стратегию проб

- [x] Избыточная нагрузка на ThreadPool из-за массового `Task.Run` для ping
  - Где: [Tracer/Program.cs](Tracer/Program.cs#L124)
  - Риск: деградация производительности при большом числе хопов
  - Действие: перейти на `SendPingAsync`, ограничить параллелизм, уменьшить/параметризовать количество проб

### P1
- [x] Полное подавление `AggregateException`
  - Где: [Tracer/Program.cs](Tracer/Program.cs#L57), [Tracer/Program.cs](Tracer/Program.cs#L59)
  - Риск: скрытие дефектов и сложная поддержка
  - Действие: разделять `Canceled`/ошибки, логировать ошибки хотя бы в verbose-режиме

- [x] Потенциальные проблемы в non-interactive окружениях (`Console.Clear`, позиционирование курсора)
  - Где: [Tracer/Program.cs](Tracer/Program.cs#L32), [Tracer/Program.cs](Tracer/Program.cs#L178)
  - Риск: падения/некорректный вывод при redirect/CI
  - Действие: fallback-режим для `Console.IsOutputRedirected`

- [x] Неверный код возврата для успешного сценария `-v`
  - Где: [Tracer/Program.cs](Tracer/Program.cs#L14)
  - Риск: внешние скрипты считают запуск ошибочным
  - Действие: возвращать `0`

### P2
- [x] Лишний прогревочный ping без использования результата
  - Где: [Tracer/Program.cs](Tracer/Program.cs#L27), [Tracer/Program.cs](Tracer/Program.cs#L29)
  - Риск: лишняя задержка и сетевой запрос на старте
  - Действие: удалить или обосновать и обрабатывать результат

- [x] Неполная обработка DNS-ошибок
  - Где: [Tracer/Program.cs](Tracer/Program.cs#L157), [Tracer/Program.cs](Tracer/Program.cs#L165)
  - Риск: аварийное завершение на временных DNS-сбоях
  - Действие: расширить обработку SocketError и пользовательские сообщения

## 2) Модернизация (улучшения)

- [ ] Добавить CLI-параметры: `max-ttl`, `timeout-ms`, `probes-per-hop`, `no-dns`, `json`
  - Прогресс: реализованы `--max-ttl`, `--timeout-ms`, `--probes-per-hop`
  - Осталось: `--no-dns`, `--json`
- [ ] Перейти на более структурный парсинг аргументов (например, System.CommandLine)
- [ ] Улучшить метрики по хопу: `min/max/avg/loss/jitter`
- [ ] Разделить логику на слои: трассировка, модель результата, вывод в консоль
- [ ] Добавить `CancellationToken` верхнего уровня (корректная остановка по Ctrl+C)

## 3) Рекомендованный порядок работ

1. Исправить критические проблемы (P0-P1)
2. Закрыть быстрые дефекты с низкой стоимостью (`-v` код возврата, лишний ping)
3. Выполнить точечную модернизацию, не меняющую поведение по умолчанию (CLI-параметры, fallback-вывод)
4. Затем делать архитектурную модернизацию (слои, расширенные метрики, форматы вывода)

## 4) Что делать первым: исправления или модернизация

Рекомендуется начать с исправления проблем.

Причины:
- исправления снижают риск регрессий и нестабильности
- модернизацию проще выполнять на предсказуемой базе
- часть исправлений очень дешевая по времени и сразу повышает надежность

Практически: сначала P0/P1, потом умеренная модернизация, затем крупный рефакторинг.
